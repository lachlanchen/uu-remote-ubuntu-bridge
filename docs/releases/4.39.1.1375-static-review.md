[`4.39.2.1561`](4.39.2.1561-static-review.md) release.

compatibility patch. It is not a live-promotion acceptance record. Proprietary
binaries, raw logs, account identifiers, tokens, and host-specific paths remain

## Upstream input-path change

Version 4.39 rewrote the relevant input code rather than merely shifting the
old instructions. The 4.33/4.34 masked signatures therefore produced no
candidates and were not reused. New semantic strings show that the vendor now
implements an explicit user-mode fallback:

- `gvinput_open result=failed fallback=send_input`
- `gvinput_send result=degraded reason=driver_injection_failed fallback=send_input`
- `gvinput_send result=failed fallback=send_input code=`

`USER32.dll!SendInput` remains an imported API. This fallback is the route the
bridge's bounded input hook already supports.

## Reviewed instruction sites

The PE section map, exception-function boundaries, source-file landmarks, and
complete surrounding control flow were inspected with `objdump`, `strings`,
`xxd`, and a RIP-relative cross-reference scan. Three unique signatures are the
new semantic equivalents of the older four-site patch:

| File offset | Function behavior | Change |
| --- | --- | --- |
| `0x5a95e6` | Constructor copies its incoming virtual-input Boolean to object offset `0x1b9` | Zero the temporary register before the unchanged store |
| `0x596412` | Persisted setting reader stores `(value == 2)` into its Boolean result | Force the result register to false |
| `0x5964c4` | Runtime setting updater copies its Boolean argument into a saved register and later stores it | Force the saved register to false |

Each full signature occurs exactly once in the original server. Replacements
are the same length, preserve instruction boundaries and surrounding control
flow, and affect only the virtual-input Boolean. The constructor's previous
separate default and setting-load sites have become one incoming argument,
which is why 4.39 needs three sites rather than four.

## Disposable-prefix and cold-start results

The signed-in production `4.33.0.8907` prefix was stopped cleanly and copied
before testing. The official `4.39.1.1375` installer and reviewed patch were
applied only to that copy. The login-registry digest and all account-bearing
user/shared caches remained byte-identical across the in-place update.

The copied prefix then completed a genuinely stopped cold start through the
normal bridge, direct-X11 input broker, native VNC desktop relay, and existing
XRDP desktop. The `4.39.1.1375` CLI responded throughout a 300-second sample;
the transient bridge stayed alive, used no swap, and was stopped cleanly. The
production `4.33.0.8907` service was restored after every canary run.

Version 4.39 writes its main server diagnostics in a new binary `.slog` format,
so the old plaintext `update_gvinput` and `room_state_changed` grep is not
valid evidence for this version. Process liveness alone is not substituted for
that evidence. A separate Windows UU controller accepted guarded
connect/disconnect requests, but did not create a visible interactive session;
the canary broker consequently recorded zero controller input events.

The manifest therefore intentionally has no `acceptance` object. Live
promotion remains closed until a real controller connects to the disposable
prefix; proves mouse, physical keyboard, mobile IME/dictation, CJK, symbols,
shortcuts, clipboard, and native terminal behavior; disconnects and
reconnects; and the same runtime passes a service restart check. This preserves
the lesson from the withdrawn 4.34 acceptance: static correctness and a warm or
noninteractive canary are necessary but not sufficient.
