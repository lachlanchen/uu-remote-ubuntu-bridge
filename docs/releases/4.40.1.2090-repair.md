# UU 4.40.1.2090 compatibility repair

## Why an existing installation can need repair

An installed server reported `4.40.1.2090` through the vendor CLI while
`compat/release-manifest.json` still described `4.39.2.1561`. The server had
the original, unpatched 4.40.1 hash, the vendor health monitor and `devcon.exe`
had returned, and `bin/powershell.exe` plus the native terminal handoff were
missing. The bridge processes were still running; an active systemd unit was
not proof of a coherent installation. The cached official setup and its
installation records were also present. This is consistent with an in-place
vendor update replacing the managed `bin` directory.

Do not falsify the installed version, ignore hash failures, or reuse old
offsets to make a verifier green. Read the actual PE/version identity, compare
against the extracted exact installer, and review each changed patch target.

## Recovery procedure

For this precise version, first verify that the current executable is either
the approved original or patched binary:

```bash
manifest=patches/uu-remote-4.40.1.2090.json
prefix="$HOME/.local/share/wineprefixes/uu-remote"
python3 scripts/patch-gameviewer.py verify \
  "$prefix/drive_c/Program Files/Netease/GameViewer/bin/GameViewerServer.exe" \
  --manifest "$manifest"
```

Before changing the live service, arrange an independent SSH/local management
path, stop only the UU bridge and its dedicated Wine prefix, and snapshot the
**complete** prefix plus installed UU scripts, systemd units/drop-ins, desktop
launchers, and bridge configuration. Keep the snapshot private. Verify free
space first. Do not use a running-prefix copy as the final rollback image.

After that snapshot, repair the already installed release without executing a
new product installer or opening account login:

```bash
./install.sh --skip-packages --skip-account-login --no-start \
  --release-manifest "$manifest"
```

Compare the stopped-prefix login registry digest and account-cache content
using the existing `login_state` / `login_state_is_preserved` functions in
`scripts/promote-approved-release.py`. Require exact preservation before
starting the service; preserve the saved environment and audio drop-ins too.
Then run both immediate and sustained verification:

```bash
systemctl --user start uu-remote-bridge.service
./scripts/verify.sh --quick
./scripts/verify.sh --stability-seconds 270
./uninstall.sh --dry-run
```

On failure, stop UU, retain the failed prefix for diagnosis, restore the saved
prefix **and** installed runtime/configuration, reload user systemd, and start
the old bridge. Do not restart GNOME, SSH, XRDP, or unrelated Wine sessions.
No account data, screenshots, raw logs, or proprietary executables belong in
this repository.

## Preventing the same drift

Managed UU launchers now include `upgrade.exe=d` in their process-local Wine
module overrides. A harmless isolated executable named `Upgrade.exe` is
blocked, while the identical executable under another name still returns its
expected exit code. This prevents the known vendor upgrade entry point from
silently replacing compatibility files in that process tree. It does not
modify the installer binary or globally disable updates for other Wine apps.

Use the guarded bridge upgrader for product updates. This guard is not a
promise against every future vendor update mechanism, manual execution in an
unmanaged Wine process, or filesystem changes by another program. Continue
checking the exact live binary, health-monitor backup, terminal proxy, account
state, and input path. Do not enable automatic promotion or paid AI repair as
part of a runtime repair.

## Latest release is a separate decision

The official endpoint served `4.42.1.2835` during this investigation. Its
installer SHA-256 is
`d3a7776f6fb00b196e2fcbf8acba06fd52b19437b0da80fec0ae838ee362f06f`.
It was downloaded and staged privately, **not promoted**.

Its constructor is now 1,828 bytes and the old constructor signature is absent.
The virtual-input Boolean moved from object offset `0x1b9` to `0x268`, and the
old `gvinput_*` fallback landmarks were replaced by a send-input/VHID backend.
The setting-reader and setter bodies remain equivalent, but that does not
establish end-to-end compatibility for the changed backend. A new patch needs
separate review and a disposable-prefix/controller acceptance run. Keep the
working 4.40.1 runtime until then.

## Workstation result, 2026-10-01

- The stopped-prefix snapshot was retained; account state and the complete
  saved input/desktop environment compared exactly before service startup.
- Full live verification passed, followed by 270 seconds with one server PID
  and zero GNOME RDP descriptor growth. Boot startup remains enabled.
- The private relay capture showed the existing physical desktop at
  1920x1080; the saved account could list its devices.
- The restored installed terminal proxy ran a fresh Ubuntu PTY command,
  returned the expected marker and Linux kernel name, and exited cleanly.
- All six isolated runtime scripts listed above passed. The source suite ran
  159 tests with the optional service test skipped; that test passed when
  invoked separately against its disposable unit.
- No reboot, fresh remote-controller phone test, or new bidirectional
  desktop-clipboard acceptance was performed. Latest-product promotion and
  automatic maintenance timers were not enabled.
