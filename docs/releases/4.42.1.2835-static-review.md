# UU 4.42.1.2835 review

This is a static compatibility review, not an unattended promotion acceptance.
The working 4.40.1 installation must remain recoverable while this candidate
is tested. No proprietary executable or account data is included here.

The installer was downloaded from the official release endpoint and extracted
through the networkless systemd staging sandbox. Its server is AMD64/x86-64,
which includes Intel processors; that PE architecture name does not require
an AMD processor. ARM is a different, currently unsupported target.

The official installer is named `4.42.1.2835`, but the extracted server,
desktop client, and CLI all have PE FileVersion/ProductVersion `4.42.0.2770`.
The running CLI reports that same `4.42.0.2770`. This exact discrepancy is
recorded as `server.reported_version`; it does not relax any artifact hash.
Readiness now requires both that exact CLI version and a fresh nonce echoed
through the running application's local IPC. A standalone `version` command
alone is not evidence that the application IPC works.

## Changed input backend

The old constructor signature is absent. Do not relax the hash check or apply
the old offsets. The new PE exception-bounded constructor is at RVA
`0x5d02a0..0x5d09c4` and stores its virtual-input Boolean at object offset
`0x268`, rather than `0x1b9`. The same field is read for the
`virtual switch state:` diagnostic and the virtual-input conditional branch.
The seven-byte argument load is replaced by `xor eax,eax` and five NOPs;
the field store and neighboring initialization remain unchanged.

The complete setting-reader and runtime-setter instruction sequences retain
the previous release's behavior. The setter's short masked signature has four
candidates; only its full exact signature and enclosing setting function
identify the reviewed location.

| File offset | Behavior |
| --- | --- |
| `0x5cfa20` | Force the constructor's virtual-input Boolean false |
| `0x5a78e2` | Return false from the persisted virtual-input setting |
| `0x5a7994` | Force the runtime virtual-input setter false |

The former `gvinput_*` diagnostics are replaced by a SendInput/VHID backend.
Its factory at RVA `0xdaf5b0` reports `backend=send_input` and installs a
callback at RVA `0xdb4cc0`. That callback checks a nonzero UINT-sized event
count and tail-calls the imported `USER32!SendInput` with `sizeof(INPUT)=40`.
The backend selector at RVA `0xdb4d40` has an explicit false branch releasing
the VHID backend; unsuccessful VHID activation reports that SendInput remains
current. The patch does not change this backend code, bypass authentication,
or grant device access. Runtime/controller tests are still needed to prove
that events reach this path under Wine.

Tools used: `pefile` for section/import/exception mappings, `objdump -d -M intel`
for bounded disassembly, and the repository's audit/patch tools for unique
signature, full-file hash, patch, verification, and restoration checks. Map
file offsets through the actual PE section: `.text` and `.rdata` do not share
one universal file-offset-to-RVA delta.

Patch, exact patched-hash verification, and byte-identical restoration passed
on a disposable server copy. The manifest deliberately has no `acceptance`
object. The usual controller, reconnect, login-preservation, service-restart,
and sustained runtime gates remain required for unattended promotion.

## Restart hang found during the canary

The old 4.40.1 bridge failed to stop one GNOME Remote Desktop child during
the first candidate switch. It remained in uninterruptible sleep and retained
the session bus name, preventing a replacement relay from starting. Its
kernel stack and pending `newfstatat` argument identified a request to its own
`/run/user/<uid>/gnome-remote-desktop/cliprdr-*` FUSE mount, not an upstream UU
login failure or an ordinary TCP/network outage.

GNOME 46.3's [`grd-rdp-fuse-clipboard.c`](https://github.com/GNOME/gnome-remote-desktop/blob/46.3/src/grd-rdp-fuse-clipboard.c)
requests FUSE exit, then calls `stat(mount_path)` to wake the session thread
before joining it. In this observed shutdown the stat request could no longer
be serviced. Aborting only that confirmed connection allowed the process to
exit without restarting GNOME, SSH, or the machine.

`scripts/release-grd-clipboard.py` implements that narrowly scoped recovery
after the launcher's TERM grace period and before its final KILL pass. It
requires the same UID and cgroup, the GRD executable, state D, the exact FUSE
wait reason, an open `/dev/fuse` descriptor whose `fdinfo` names the connection,
a matching user-owned GRD clipboard mount, and a pending request. It rechecks
process identity and mount ownership before writing `abort`. An older kernel
without the `fuse_connection` fdinfo field is a safe no-op. It does not abort
all FUSE mounts, inspect clipboard contents, or disable clipboard support.
Connection numbers are reusable: never hardcode a number from an earlier run.

## Working-version checkpoint

The prior bridge source is tagged and pushed as
`uu-4.40.1.2090-working-20261001` at commit `5532d49`.
The tag is not a copy of the installed Windows application or its login.

On the workstation, a separate private checkpoint contains the complete
cleanly stopped 4.40.1 Wine prefix, installed UU launchers/helpers, user service
units and drop-ins, environment/audio settings, and a Git bundle of that tag.
Every regular file was checksum-compared with its stopped source; symlinks and
modes were compared too. The service restarted and passed quick verification
after the snapshot. The restore helper checks the snapshot before making
changes, defaults to dry-run, preserves displaced files, and restores the
prior files if the replacement transaction fails. Account-bearing checkpoints
must never be uploaded to GitHub.

For this checkpoint on the original workstation:

```bash
checkpoint="$HOME/.local/state/uu-working-checkpoints/4.40.1.2090-20261001"
python3 "$checkpoint/restore.py" verify "$checkpoint"
python3 "$checkpoint/restore.py" restore "$checkpoint"  # dry-run
# From an independent SSH/local terminal, only when rollback is needed:
python3 "$checkpoint/restore.py" restore "$checkpoint" --apply
```

Restoration briefly stops UU, not GNOME or SSH. Leave automatic maintenance
disabled during candidate tests. Keep sufficient free space for a fresh copy
and retain the checkpoint until the new version has passed real controller
testing. Source can be recovered independently from `source.bundle`; run the
tagged source's verifier after restoration, since a newer checkout may quite
correctly report a source-digest mismatch against the old runtime.

## Canary result, 1 October 2026

The installer was applied only to a separate copy of the stopped checkpoint,
inside the staging sandbox. Installation and bridge preparation preserved the
login-registry digest and every recorded `user_cache` and `shared_state` file.
A temporary runtime-only service override selected that prefix; a timed return
to the untouched production prefix was armed before the test.

Observed on the x86-64 GNOME Wayland workstation:

- The patched 4.42 server started, local IPC answered, the native Mac UU
  controller displayed the physical desktop, and exact English typing reached
  a separate GTK test editor during the initial connection.
- The installed PowerShell compatibility executable reached the native Linux
  PTY, returned an exact marker and `Linux`, and exited successfully. This is
  a local installed-proxy test, not an end-to-end vendor terminal test.
- One server PID survived the 270-second stability gate; GRD descriptor growth
  was zero. The first measurement explicitly allowed source drift while the
  shutdown fix was being edited. A later full runtime installation matched
  the source digest; these are separate checks, not one acceptance record.
- Further service stops and starts completed without leaving a stuck GRD
  child. The automatic FUSE-abort branch was covered by targeted fixtures;
  the original live stuck connection was recovered manually after ownership
  verification. Do not claim the hang was reproduced and automatically fixed
  on every later restart.
- Post-restart controller tests did not produce consistent fixture evidence.
  Some test input reached GNOME Overview instead of the editor. This does not
  prove a vendor input regression, but is insufficient for promotion.

The canary was withdrawn. The runtime override was removed and **4.40.1.2090
was restarted from its original prefix**. Automatic maintenance remains off.
The timed rollback was canceled only after the explicit return succeeded.
The complete private checkpoint remains unchanged.

With the shared bridge clipboard fix active on 4.40.1, the native Mac client
delivered an exact English string and multiline English/Chinese paste to the
GTK editor. Original Mac pasteboard items and types were restored after the
test. The isolated controller-clipboard test also passed its owner filter,
startup baseline, Unicode, missing-xclip, bounded-timeout, and cleanup checks.

Remaining release gates include a repeatable post-restart mouse/keyboard
fixture, controller clipboard in both claimed directions, real mobile IME
and continuous dictation, and the vendor's remote terminal/file-transfer
workflows. There is no new claim of bidirectional clipboard support: the
additional companion deliberately forwards controller-to-host text only.
Neither this static manifest nor the working-version tag enables unattended
promotion of 4.42.

## Final working-runtime verification

The committed bridge changes at `3a73148` were installed through:

```bash
./scripts/upgrade-uu-remote.sh apply --runtime-only --now --no-pull
```

This kept the installed product at 4.40.1.2090, made a separate runtime
transaction backup, and passed the exact source-digest check. The saved
environment remained byte-identical to the pre-canary checkpoint; the audio
isolation drop-in remained present. A subsequent 270-second verification
passed with one stable server PID and zero GRD descriptor growth. The service
reported zero automatic restarts. Both startup units remain enabled; the
update and repair timers remain disabled. No machine reboot was performed.

All 173 repository tests passed with `UURB_TEST_SYSTEMD=1`, including the
isolated service-recovery test. The isolated controller-clipboard and RDP
semantic-text tests passed. The installed 4.40 terminal proxy also returned
the expected marker, Linux identity, and successful exit. These checks do not
replace the pending real phone/controller release gates above.

The private checkpoint was reverified after the work: files, symlinks, modes,
and source bundle still match its inventory. Test windows and the test-only
Mac UU connection were closed. The maintainer requested ARM tester cooperation
on [issue #12](https://github.com/lachlanchen/uu-remote-ubuntu-bridge/issues/12#issuecomment-5921816874);
ARM support remains unverified, not a resolved compatibility claim.

The disabled updater's status output may still show its historical August
maintenance snapshot. The live installed manifest and verifier, not that
stale cached status, identify the running 4.40.1 product. Do not enable repair
timers merely to refresh that display.
